# Everyday development launcher: operation and live cutover

## Current boundary

The source launcher publishes immutable generations and acquires an authenticated development host; it no longer uses the earlier fail-closed-only stub. This is a development workflow, not the packaged singleton launcher. **The installed `/Users/bryancostanich/bin/cercano` remains the old script. Live cutover is not complete and requires approval.** Actual A/B acceptance is ongoing; this guide does not assert that it or any tests passed.

The workflow never implicitly stops the old app, imports its database, or migrates its configuration. The one-time transition creates **separate new state**, not a replacement for or loss of the old data. Do not point it at your existing Cercano state, copy a legacy database into it, or use a running production launcher to provision it. Existing sessions continue on their original hosts until explicitly managed.

## Bootstrap once, in a new private state

Prerequisites: Python 3.9+, the supported native Go build toolchain, and on macOS working ad-hoc codesigning. Use canonical absolute paths without symlink aliases. The state parent must already exist; the state directory itself must **not** exist (even an empty directory is rejected).

The normal launcher requires a prepared store before it can build. Break that bootstrap dependency with the **build-only publisher outside the new state**, then invoke that published binary's early `prepare-development` command. That command calls `PrepareDevelopmentStore`, creates the directory with mode 0700 and a development-owned v2 store, and does not enter ordinary startup or read config, legacy state, or credentials.

Example, to run only when explicitly ready to provision isolated development state (not as part of the static cutover checks below):

```bash
# Set REPO to the reviewed source checkout you intend to use.
REPO=/absolute/canonical/repository
export CERCANO_REPO="$REPO"
umask 077
BOOTSTRAP=$(mktemp -d /tmp/cercano-bootstrap.XXXXXX)
BOOTSTRAP=$(python3 -c 'import os,sys; print(os.path.realpath(sys.argv[1]))' "$BOOTSTRAP")
GEN=$(CERCANO_DISABLE_CREDENTIALS=1 python3 \
  "$REPO/source/server/scripts/publish-dev-generation.py" publish \
  --repo "$REPO" --root "$BOOTSTRAP" --generation bootstrap --sign)
# Parent exists; this exact leaf must be NEW. Choose your own separate path.
export CERCANO_DEVELOPMENT_STATE=/absolute/canonical/existing-parent/cercano-development-NEW
"$GEN/cercano" prepare-development --new-state "$CERCANO_DEVELOPMENT_STATE"
```

Do not `mkdir` the NEW leaf yourself. Failed provisioning leaves it for inspection; retry cannot adopt it. Choose another new destination only after understanding the failure. Nothing automatically deletes the bootstrap publication or partially prepared state.

Next explicitly author `$CERCANO_DEVELOPMENT_STATE/config.yaml` as an owned private regular file (0600). It is required, not generated by preparation. Use reviewed settings rather than copying secrets or relying on implicit legacy/environment migration. For a cloud-only route, for example:

```yaml
locus_mode: cloud_only
active_cloud_profile: work
cloud_profiles:
  - name: work
    provider: openai
    flavor: chat_completions
    model: your-configured-model
```

Replace the model/profile with an intentionally configured supported route. Credentials must already be provisioned separately for that profile. Production dependency construction can read native credentials **read-only**, after store preflight; it is not credential-free just because the child environment disables ordinary credential startup. Shared configuration/auth mutation, credential migration, login/refresh writes and setup changes are not supported through this host. Do not use this guide's examples to touch real credentials during candidate validation. Build commands do not need them.

### Cloud versus local prerequisites

`cloud_only` is supported without `modelhost.yaml`, a local runtime, or an embedding engine. It uses the configured real cloud provider; this does not guarantee credential/network/inference success or provide an open-model fallback.

Local `open_only` and mixed lanes instead need an **already-running, API-compatible coexistence-protected modelhost**, with selected models configured and prewarmed. Place an explicit private regular `modelhost.yaml` in the new state:

```yaml
run_dir: /absolute/canonical/private/protected-modelhost-record-directory
```

This pins the exact protected record directory. Ordinary pre-existing unprotected modelhosts are not sufficient. The host verifies the protection assertion and attaches only; it does not bootstrap, upgrade, launch, replace or prewarm the runtime. Local cold starts are unsupported here. Supported engines are `llama_server` and `mistralrs`, not Ollama or an in-process fallback. See [prepared dependency details](../../source/server/cmd/cercano/development_host_production.md).

## Everyday launch, reuse, and exact reconnect

Set `CERCANO_DEVELOPMENT_STATE` and, when intentionally overriding the embedded checkout, `CERCANO_REPO` in every shell. Invoke the reviewed source entrypoint, or the installed launcher only **after approved cutover**:

```bash
"$CERCANO_REPO/source/server/scripts/cercano-launcher.sh"
```

A plain invocation fingerprints source/toolchain inputs, publishes or validates a complete signed generation under `state/generations`, then acquires a **new conversation**. Same inputs reuse the generation and authenticated host; they do not reconnect a prior conversation. Same-generation host acquisition is serialized, including concurrent callers; distinct conversations can share that host. Source changes select another generation, leaving prior binaries and sessions intact. Fingerprints include all `source/` bytes, including untracked/ignored inputs, so apparent “same Git commit” alone does not imply reuse. Fingerprinting can be expensive.

Runtime socket paths must be short: `CERCANO_RUNTIME_ROOT`, if supplied, must name an existing canonical owned private directory whose resolved path is at most **38 bytes**. Otherwise the launcher creates a short private `/tmp/cd-*` root and saves its path in `state/runtime-root.json` under a lock. Keep that directory available; a missing saved root is a failure, not permission to discover a replacement runtime.

Acquisition writes a private immutable selection in `state/selections/<conversation>.json`. Identify and save the **exact selection for your conversation**, not “latest” by timestamp (concurrent invocations make that ambiguous). It contains generation, endpoint, token-file path, host/build/store identity, conversation and ownership epoch. Treat selection and token material as private; do not edit identities or overwrite original selections.

```bash
SELECTION="$CERCANO_DEVELOPMENT_STATE/selections/EXACT-CONVERSATION.json"
"$CERCANO_REPO/source/server/scripts/cercano-launcher.sh" --dev-host "$SELECTION"
```

Explicit `--dev-host` validates that saved generation and executes its pinned CLI; it neither builds current source nor creates a new attachment owner/host. It must validate the same authenticated host and epoch. Exiting the TUI or `/host detach` **retains ownership and independent work**; `/host reconnect` reconnects that exact owner. Do not substitute a plain invocation when the intent is to resume.

## Explicit lifecycle management

In the TUI, `/host list` reports lifecycle state. `/host detach` closes the attachment, not the task or host. Detach before `/host release`, `/host retire`, `/host acquire`, `/host transfer <destination.json> <unique-handover-id>` or `/host claim <destination.json> <handover-id> <receipt>`. `/host reconnect` reattaches after management when the retained owner is still valid.

Management-only CLI calls do not attach a TUI:

```bash
LAUNCHER="$CERCANO_REPO/source/server/scripts/cercano-launcher.sh"
"$LAUNCHER" --dev-host "$SELECTION" --dev-host-action list
# Only after attachments/work have drained and you intend to relinquish ownership:
"$LAUNCHER" --dev-host "$SELECTION" --dev-host-action release
# Only after all ownership/work has drained and retirement is intended:
"$LAUNCHER" --dev-host "$SELECTION" --dev-host-action retire
```

Release relinquishes the conversation owner; retire retires the host, not just the current TUI. Server admission checks remain authoritative: live attachments, running independent work, callbacks and unresolved ownership/handover state can block release, transfer or retirement. A refusal is not an invitation to kill the process or delete records. Inspect `list` and private host logs; wait for work to finish or resolve the specific outstanding work explicitly. Unrelated owners remain protected.

Transfer requires an exact compatible destination selection and unique handover ID:

```bash
"$LAUNCHER" --dev-host "$SELECTION" --dev-host-action transfer \
  --dev-host-destination "$DESTINATION_SELECTION" --dev-host-handover "$HANDOVER_ID"
# Only if the result is pending: preserve the returned receipt and retry claim explicitly.
"$LAUNCHER" --dev-host "$SELECTION" --dev-host-action claim \
  --dev-host-destination "$DESTINATION_SELECTION" --dev-host-handover "$HANDOVER_ID" \
  --dev-host-receipt "$RECEIPT"
```

Pending is unresolved work, not success. Preserve the receipt/ID; do not begin a fresh transfer to bypass it. Successful CLI transfer/claim returns `Selection` in its JSON output; it does **not** rewrite the original selection file. Save the returned selection privately as a new file under this state's `selections/` for subsequent exact reconnect, or use the TUI's updated in-memory selection. Old epochs are not valid substitutes.

A recorded host that is unreachable or retired is **never automatically respawned**. A failed start retains a durable `.starting` intent and logs; later calls refuse replacement. Even after retirement, a plain same-generation invocation is not a restart mechanism. There is no documented automatic repair/garbage-collection command here: preserve evidence and resolve the record deliberately under a separately reviewed recovery procedure. Do not delete locks, intents, host records, tokens, generations or state to force retry. There is no automatic deletion or retention sweep of published generations or old data.

## Live launcher cutover: preparation only, approval still required

Target: `/Users/bryancostanich/bin/cercano`. **Do not execute the old script, install over it, or run a candidate against production.** Do not touch real application state or native credentials. The installer is explicit and no-clobber; it cannot replace an existing file or symlink and has no `--force` path.

After the implementation lands in the **main repository**, the main operator can prepare a candidate with the following commands. Confirm `MAIN` is the actual canonical main checkout containing the landed revision, not this feature worktree. The example main path is intentional and must be verified by the operator; it was not inspected for this documentation task. The installer embeds its own checkout root, so invoking the worktree installer and planning to override `CERCANO_REPO` later is not an acceptable installed artifact.

```bash
MAIN=/Users/bryancostanich/git_repos/cercano-ai/Cercano
OLD=/Users/bryancostanich/bin/cercano
umask 077
STAGE=$(mktemp -d /tmp/cercano-cutover.XXXXXX)
STAGE=$(python3 -c 'import os,sys; print(os.path.realpath(sys.argv[1]))' "$STAGE")
# Read-only evidence of the installed file; never invoke it.
shasum -a 256 "$OLD" > "$STAGE/installed.before.sha256"
stat -f '%N %Sp %u:%g %z %m' "$OLD" > "$STAGE/installed.before.stat"
bash "$MAIN/source/server/scripts/install-launcher.sh" --destination "$STAGE/cercano"
bash -n "$STAGE/cercano"
bash -n "$MAIN/source/server/scripts/cercano-launcher.sh"
# Parse Python without importing/executing it or writing __pycache__.
python3 - "$MAIN/source/server/scripts/cercano-launcher.py" <<'PY'
import ast, pathlib, sys
ast.parse(pathlib.Path(sys.argv[1]).read_text(), filename=sys.argv[1])
PY
# Inspect embedded default and compare bytes; diff exit 1 means different, not failure.
grep -n 'REPO=' "$STAGE/cercano"
if cmp -s "$OLD" "$STAGE/cercano"; then
  echo 'Candidate unexpectedly identical; investigate before approval'
else
  diff -u "$OLD" "$STAGE/cercano" > "$STAGE/launcher.diff" || test "$?" -eq 1
fi
shasum -a 256 "$OLD" > "$STAGE/installed.after.sha256"
stat -f '%N %Sp %u:%g %z %m' "$OLD" > "$STAGE/installed.after.stat"
cmp "$STAGE/installed.before.sha256" "$STAGE/installed.after.sha256"
cmp "$STAGE/installed.before.stat" "$STAGE/installed.after.stat"
shasum -a 256 "$STAGE/cercano" > "$STAGE/candidate.sha256"
printf 'Review candidate and evidence in %s; installed path untouched\n' "$STAGE"
```

These are **commands to prepare**, not evidence of execution. They stage only in a new private temp directory, inspect the original read-only, and perform syntax/static checks without executing either launcher. Static success does not demonstrate isolation, A/B behavior, credential safety or runtime acceptance. Main can perform actual artifact validation after landing. Retain the original hash, diff and candidate hash for review.

Stop before activation. Approval must cover acceptance evidence (including the ongoing actual A/B exercise), the landed revision, embedded main path, candidate hash and a separately agreed replacement/rollback operation preserving the original script. No replacement command is authorized here. Until then the installed script remains old, and the everyday workflow/live cutover is **not complete**.

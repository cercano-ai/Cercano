# Cross-platform updates — one native macOS temporary-install milestone

## Status, authority, and signoff

The user approved the architecture and bounded native macOS temporary-install milestone on 2026-10-22 and authorized these clarifications plus a focused replacement `plan.md` for approval. The implementation plan remains **pending user approval**; this documentation revision authorizes no implementation or execution. Historical plans and evidence are context, not authority to execute superseded tasks.

The only next milestone is **one real end-to-end update in an isolated, per-user temporary installation on native macOS Apple Silicon**: acquisition → verification → staging → announcement → reversible drain → proof that relevant clients and agent have exited → selection publication → manual normal start → outcome report. Unit tests, fixture-only transactions, cross-compilation and version output alone do not complete this milestone.

This revision replaces, rather than appends exceptions to, the earlier architecture. Specifically superseded are Windows-first ordering; normal launcher/child dependence on SQLite, activation journals or persisted executable manifests; completed/healthy/candidate-transaction startup eligibility; universal prior-reader compatibility qualification; automatic candidate restart/health-driven rollback; deletion after health success; and mandatory production integration of updater-specific force authorization/save-failure machinery. Previous approvals and verification reports remain historical evidence, not simultaneous requirements for this milestone.

## Approved constraints

- Package a **dedicated short-lived updater executable with each normal complete release**. No separate updater distribution, updater daemon, listening control service or general process registry. No Velopack.
- Reuse existing acquisition, archive validation/staging, selection publication, independent process launch and native process-lifetime primitives. Adapt integration boundaries rather than building a second update engine. Already-built isolated primitives are not shipped end-to-end integration.
- Agent and CLI, both stable launcher and versioned child, start independently of updater SQL, journals, manifests and operation state. An intact selected release must boot when that bookkeeping is absent, corrupt or inaccessible.
- Use minimal installation-scoped, OS-held launch exclusion; lock ownership is tied to a live process and released by the OS on crash. Normal launches never consult transaction state to decide whether to wait or start.
- Preserve installation ownership. No live enrollment, developer-installation replacement, Homebrew link changes, package-manager bypass, production signing/feed changes or release publication is authorized. Windows/Linux installed-system acceptance and package-manager integration are deferred.
- Keep previous versions. No automatic rollback, health-triggered deletion, retention collector or sophisticated cleanup. Selection reversal cannot reverse candidate writes to databases, configuration, credentials or external systems.

## Release layout, trust, and independent startup

Use the existing explicitly enrolled temporary-install layout: protected installer-owned installation identity, stable public agent/CLI entrypoints, a small selection record, and complete immutable version directories. A release contains the agent, CLI and dedicated updater. The running updater executes by exact path from the **retained immutable old version directory**; it never replaces, renames away or deletes its own executable/image directory. This rule also governs future Windows support. The new directory contains the *next* updater version; subsequent updates launch that version. Stable launcher replacement/bootstrap upgrades are not part of this milestone.

Acquisition must authenticate the exact platform/architecture target through the existing TUF boundary, enforce target size/hash and downgrade policy, and retain archive checks against traversal, duplicate/unexpected/missing members, symlink escapes and oversized content. Stage a whole release before making it selectable. Extend existing package/member validation to include the dedicated updater rather than assuming an agent/client pair is sufficient. Use ephemeral test keys and a local test repository for acceptance; matching unsigned checksums are not publisher authentication. Production Apple signing/notarization and TUF operations remain separate release gates, not implied by temporary-install tests.

Startup's authority is the protected installation identity and validated selection/layout, **not updater recovery records**. Both stable launcher roles and both child startup paths must validate installation identity, selection syntax and supported layout, exact role, and regular executable containment inside the selected immutable version directory. Reject malformed/ambiguous selection, missing executables, traversal, escaped symlinks, wrong installation/role and unsafe ownership/permissions. Locators remain locators, never executable-path or digest authority. Missing/corrupt selection fails closed; missing/corrupt updater bookkeeping does not. This is not permission to search PATH, guess another release, silently enroll, or bypass installation/path checks.

Remove updater-record verification from the ordinary boot dependency graph, including indirect startup notices/control-identity initialization. Optional updater reporting may degrade to “outcome unavailable”; it must neither repair/migrate updater state during boot nor prevent normal initialization. Keep acquisition-time authenticity and immutable-install protection; do not replace SQL-bound manifests with another mandatory updater manifest boot gate.

Forward safety remains required: the old updater must understand the candidate's target/package/selection contract, and the candidate must safely read the actual prior application state for the tested transition. Unknown required formats or unsupported migrations must refuse this update before publication. Test preservation of application data and the specific forward transition; no universal backward-reader matrix or prior application's ability to read candidate writes is required. Offline preflight only establishes bounded entrypoint reachability, not state compatibility, readiness, sandboxing or safe rollback.

## Simplest recommended coordination mechanics

These mechanics are the proposed integration approach, not a claim they are already wired. Reuse `internal/updatecoord/launch` to start the exact old-release updater independently with fixed local arguments and nonblocking regular-file/discard output. It survives the initiating CLI's exit. The parent must not hold a launch/update lock the child waits on. The updater acquires its own single-writer/update exclusion, then announces readiness over the existing agent connection/event seams. An updater-owned operation/status record may support progress and a later explicit report; it is never consulted by normal startup and is not a new control service.

Use existing agent connections/event subscriptions for update announcement, drain progress, consent/cancel controls and voluntary client shutdown. A bounded update-specific exchange on those connections may carry an operation token and exact lifetime observations; it must not turn unauthenticated network RPC into authority to replace local files or kill processes. Local updater inputs and installation policy authorize publication. No general registry, new listener, polling control daemon or persistent client-registration service.

Recommended lock split: one updater-owned writer lease serializes update attempts; an installation launch barrier excludes new agent/CLI starts from the final participant census through publication/readback. Ordinary starts take only the short OS launch lease around validated selection/startup, not a process-long shared lease that would deadlock an updater waiting for existing apps to exit. Keep lock identity in installer-owned storage independent of SQL. Acquire the barrier before final census/drain so new entrants cannot appear unnoticed; in-flight startup must finish its validation/registration or fail before census is accepted. Existing clients remain able to drain and exit while the barrier is held.

Cover stable agent launch, stable CLI launch, versioned child startup, CLI initial auto-launch and every reconnect/respawn path. During the potentially lengthy drain, a launch must return a clear retryable “update in progress” result immediately or after a short bounded wait; it must not spin, wait indefinitely, or bypass exclusion. Reconnect auto-launch recognizes that result and backs off without repeatedly spawning children; cancellation remains responsive. A blocked reconnect must not fall back to a cached old binary or direct launch. Parent and child cannot wait on each other's leases: reuse the existing exec/reacquisition seam on macOS and require child validation under the barrier before normal initialization, or a proven equivalent ownership transfer. A child caught between handoff and barrier acquisition must wait/fail before admission and cannot become an unobserved old process. On updater crash, kernel release restores launch availability without consulting an abandoned transaction. The selected record remains the only boot selection.

### Exit proof and controlled complete-set handoff

Only a controlled complete-set safe cutover is required here. The harness establishes the complete initial set of installation agent/TUI processes, **including disconnected-but-live TUIs**, from its controlled launches; it is not limited to `SubscribeEvents` subscribers. It supplies a one-operation, owner-only local input file containing installation binding and exact PID/start-time/UID/executable observations to the real bundled updater by fixed argument. This is a bounded input, not a persistent registry or installation-wide discovery service. The harness prevents unlisted initial launches; the updater's OS barrier fences all subsequent launches. In-flight starts must complete before the final set is accepted or fail before initialization.

The updater itself acquires exclusion and independently re-inspects every supplied live identity with `internal/updatecoord/nativeprocess.Inspect`/`Identity.SameProcess`, verifies installation executable/role binding, and retains those observations in its own memory **before anyone is asked to depart**. Missing, changed or uncertain initial evidence refuses this attempt. Reuse the native exact-lifetime wait semantics of `internal/brewrestart/coordinator_darwin.go:waitProcessExit` (small shared extraction/adaptation, not its Homebrew coordinator): confirmed disappearance or changed birth timestamp proves the original lifetime gone; permission/query failures or identity changes without a new birth timestamp do not. The updater owns the repeated native observations and publication decision; harness exit assertions, stream loss, PID alone, accepted stop, vanished listener, rename probes and elapsed time cannot substitute.

Use a small operation-token-bound request on the existing agent RPC connection to announce updater readiness/drain ownership and an additive notice on existing `SubscribeEvents` to acknowledge that exclusion and evidence are established. The initiating client waits for that acknowledgement before voluntary exit. The disconnected TUI need not reconnect to count: it remains in updater evidence and blocks publication until it closes normally (the harness can arrange normal user exit after acknowledgement). Consent/cancel and progress use the same existing connection; no new listener. The local input authorizes only this controlled attempt, not network-provided file replacement or process killing. The readiness/drain connection lifetime releases the reversible seal on owner loss; the updater's OS lock releases on death. Missing acknowledgement aborts rather than guessing handoff success.

Hold exclusion through drain and publication/readback. Clients close normally and the agent shuts down normally after admitted work completes; uncertainty or a still-live relevant process prevents publication. Arbitrary live-installation discovery, including finding previously disconnected clients without a harness, is explicitly a **later design gate**, not an unfinished prerequisite here. Do not introduce a registry/census framework to solve it.

### Relevant workers and managed runtimes, not universal descendants

Relevance is determined by safe shutdown, admitted-work completion, package consistency or version transition, **not spawned ancestry alone**. Include all installation agent/TUI processes and the owned worker/runtime lifetimes that meet those criteria. Existing ownership supplies the bounded set; no universal descendants census or updater tree-kill.

Source check: `internal/server/server.go:Shutdown` calls the worker runner's shutdown then `stopRuntimeInstances`. `internal/worker/host.go:workerRunner.Shutdown` and `pool.go:workerPool.Shutdown` own pooled conversation workers; `spawn.go` owns process wait/reaping, and Unix teardown already targets owned worker groups. Active workers and their admitted tool continuations must finish or receive ordinary user cancellation before shutdown; idle warm workers still execute the old agent image and must be reaped before cutover. Reuse this owner bookkeeping and teardown, not updater force authorization or broad process killing. Existing group cleanup is not evidence that every descendant matters or has exited.

`cmd/cercano/main.go:buildRuntimeManager` registers managed llama-server and mistral.rs providers; `server.go:stopRuntimeInstances` lists/stops instances with a ten-second context and currently only logs failures. Their provider process helpers own managed process termination. Keep managed runtime starts/downloads and their asynchronous work in admission accounting; let admitted completion/nested launches proceed through sealing. Before these owned processes depart, relay exact relevant worker/runtime identities from these existing owners over the same bounded operation exchange and have the updater capture native evidence. A newly launched relevant continuation must complete this handoff before its owner permits departure; inability to capture evidence aborts publication, never interrupts admitted work to make the test pass. After drain, close this owner set against further starts, shut down/reap idle workers and managed instances, and require updater exit evidence. A logged stop failure or agent exit alone is insufficient. Exercise both owned-worker and managed-runtime paths, including a stop failure.

Provider ownership needs an explicit distinction: `internal/localruntime/llamaserver/provider.go:Stop` releases adopted instances without killing another owner's process, while its owned-instance path returns `killProcessWithResult` errors. `internal/localruntime/mistralrs/provider.go:Stop` preserves an adopted sidecar with a live sibling owner, otherwise calls its group terminator, and returns nil without independently establishing updater exit proof. Both mark records stopped before termination completes; neither a stopped record nor a successful manager call substitutes for native evidence. Preserve these ownership boundaries. An adopted external runtime may remain when admitted use is complete and its lifetime has no package/version-transition effect; if relevant, obtain evidence through its actual controlled owner or refuse this attempt, never kill another owner's process to satisfy acceptance. The server's ten-second context is not a guaranteed provider termination deadline because these provider `Stop` methods ignore the passed context.

External services (for example an independently operated Ollama endpoint), unrelated shell/background processes, and model files outside the selected package are not automatically update participants. Wait for the application's admitted use of them and preserve state; do not terminate them merely because they were contacted or spawned. Include an additional owned tool process only when its outstanding work or old-release lifetime affects the stated safety criteria. If ownership/completion cannot be established in this controlled run, refuse rather than expanding to tree discovery.

## Drain and cancellation contract

Announce the verified staged update and its consequences before stopping applications. Consent is explicit; acquisition/staging may run while ordinary work continues. Entering drain **immediately and reversibly seals new root work**, then waits for already-admitted work to finish. It must not wait for an idle instant while continuing to admit unrelated work.

Carry admission ownership through already-admitted continuations, nested calls, tool/worker launches and asynchronous lifetimes. Sealing cannot reject a nested admission belonging to admitted work, nor allow unrelated work to borrow that admission. Count actual work lifetimes, not observer connections. Keep passive status and ordinary cancellation controls callable, explicitly including `CancelRuntimeModelDownload`. Do not remove the user's ability to cancel an active task just because the updater is waiting for it.

Before publication, cancellation/defer/failure releases the reversible seal and exclusion, leaving selection unchanged and resuming normal admission in any surviving agent. If voluntary exits have already happened, do not claim cancelled applications were resurrected: report that manual normal start is available. Already-staged files may remain. An updater disconnect/crash before commit must not leave a permanent drain seal; tie the reversible drain lease to the existing connection/lifetime mechanism, with safe resume if its owner is lost. A graceful shutdown already committed may still complete; this is not a rollback obligation.

Updater-specific forced interruption authorization, forced save-failure choices and forced command/worker termination are disconnected from this milestone. Preserve those existing modules/evidence without making them prerequisites. Normal task cancel controls remain supported and are not “force update.”

## Publication boundary and honest outcomes

Immediately before publication, under installation launch exclusion, revalidate the staged complete target, current selection, installation identity, participant exit proof and operation ownership. Perform the **final cancellation check**. The exact non-cancellable boundary is **entering selection publication under exclusion after that check**. Cancellation before this boundary aborts/resumes; cancellation at or after it does not interrupt the publication/readback/report sequence or trigger generic undo.

Reuse existing selection publication primitives. Publish one complete selection, never individual agent/CLI replacements. Hold exclusion through bounded safe readback and outcome determination, then release it for manual normal start. Reconcile only as necessary to state what selection is actually visible; do not automatically restore old selection, delete files or require journal reconciliation on boot.

Atomic visibility is not power-loss durability. Report independently: target staged; publication entered; selected target observed (or unchanged/unknown); flush/durability result; and manual-start verification pending/succeeded/failed. If a rename became visible but a subsequent file/directory flush fails or is unsupported, report “new selection observed; durability uncertain,” not “nothing changed,” durable success, or automatic rollback. A cancelled caller context after the boundary must not suppress bounded readback/reporting. If the updater crashes there, a later explicit updater/report invocation may inspect selection and records; normal startup still ignores those records. Do not infer durability from successful readback or simulate power-loss proof with process termination alone.

Keep the previous directory and updater image for every outcome. On malformed/unknown selection, normal launch refuses safely and the report gives explicit recovery guidance; no guessed selection repair. Failure to write final updater status is distinct from publication failure and never prevents an otherwise intact selected release from starting.

## End-to-end acceptance (future implementation, not results)

Run only on native macOS arm64 against disposable roots, isolated application state/ports and a local authenticated test feed. No developer live agent, credentials or package-managed installation. The following are required in one integrated flow, with additional fault cases:

1. Start an old real agent and CLI through the temporary install's normal entrypoints. Use an actual complete candidate package containing the next updater; acquire it through TUF, verify and stage using the existing engine. Demonstrate rejection of invalid trust/target/archive inputs without changing selection.
2. Launch the packaged old updater independently. Announce the prepared update through existing connections, establish exclusion and capture participants before exit. Prove the initiating client can exit without terminating the updater; no parent-owned lock deadlock.
3. Run admitted work through immediate reversible drain, including a continuation that crosses the seal and a nested admission. Reject new root work. Exercise ordinary cancellation including runtime-model-download cancellation. Demonstrate pre-publication cancel/resume and updater crash releasing locks/seal without consulting updater transaction records on boot.
4. Obtain real native exit proof for clients, agent and relevant children before publication. Exercise a second client, disconnected live client, stop acceptance without exit, lost/uncertain identity and an attempted explicit/auto/reconnect launch during exclusion. Unknown exit prevents publication.
5. Publish the complete candidate and read back selection. Exercise cancellation on both sides of the exact boundary, crashes before/after publication and after-publication flush failure. Record visibility and durability separately; no automatic undo/deletion. Demonstrate no mixed release selection.
6. Release exclusion and **manually start normally**, not through an updater-only candidate/health exception. Verify the running agent and CLI are the expected new release and can perform a real normal interaction with preserved application state. Report publication separately from this runtime result. No automatic restart or health gate is required to boot.
7. Repeat normal agent/CLI launcher **and child** startup with updater database/journals/manifests missing and corrupt; all intact-selection cases boot. Malformed selection, containment escapes, wrong role and missing selected executable fail closed. Check incidental startup reporting cannot reintroduce the updater dependency.
8. Verify the previous version and executing old updater remain intact and the new package carries the next updater. A failed normal start leaves the candidate selected and old files retained with an honest failure report, not a rollback claim.
9. Exercise the **actual capability producer output through the actual strict consumer**, not separately hand-written fixture shapes. Resolve the `offline_preflight` producer/consumer mismatch in future integrated code while retaining strict schema validation and honest execution readiness. Offline preflight is not activation authorization.

Acceptance records must distinguish observed results from planned tests and mocks. Report exact artifact identities, native platform, temporary-install isolation, known limits and failure outcomes. Successful acquisition or existing isolated verification reports do not establish this flow has shipped.

## Source-checked integration pitfalls

- `pkg/stablelaunch/launch.go:84-110` currently opens updater SQL before acquiring exclusion and loads completed/candidate manifests. `pkg/installcontext/verify.go:31-69` independently gates child startup through completed/candidate updater verification. Both sides must change; fixing only the stable launcher does not provide independent boot.
- `internal/server/update_admission.go:46-75` waits for zero before pausing; `sealForForce` is permanent, not a reversible drain. The interceptor comments at lines 172-176 rely on nested enters being safe under that old policy. Simply sealing earlier breaks that assumption. The unary exemption list at lines 140-145 omits `CancelRuntimeModelDownload` even though its handler exists in `internal/server/server.go:2962`.
- `cmd/cercano/private_update.go:82-84` adds `offline_preflight`; `internal/updatecoord/bootstrap/capability.go:111-126` accepts exactly three older fields and rejects all others. This is an integration mismatch, not evidence that probing is ready.
- `internal/updatecoord/launch/launch.go:24-45` provides independent non-pipe output, no parent lock and asynchronous reaping, but not coordination or participant completeness. `pkg/agentclient/reconnect.go` includes respawn behavior; exclusion must cover it as well as explicit launches. Native Windows launch locks now exist (`pkg/agentclient/launch_lock_windows.go`); the old blanket “non-Unix launch lock is a no-op” baseline is not current evidence.

All source paths above are relative to `source/server/`. These are read-only inspection findings for specification design, not test execution or implementation claims.
